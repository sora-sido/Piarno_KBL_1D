## 2. 新曲「新宝島」

### 楽譜（`scores/shin_takarajima.html`）
- ユーザーが書き起こした音名・リズム（写真3枚）・指使いをもとに、右手メロディ譜を作成。abcjs で五線譜として表示。
- 構成：前奏12小節 → Aメロ28 → サビ24 → 間奏16 → サビ2 32 → 大サビ24 → 後奏28（計164小節）。
- 調号は♭2つ（シ♭・ミ♭）。テンポは前奏 ♩=149、Aメロ以降 ♩=156。
- 前奏の最後の「ソ」「ファ」は、それぞれ2小節（全音符2つをタイでつなぐ）。
- 再生ボタン付き。外部のピアノ音源が読み込めない環境があったため、Web Audio のシンセリード音（デチューンしたノコギリ波2本＋ローパスフィルター）で鳴らす。
- 再生時のテンポ切り替えを二重に計算していた不具合を修正（Aメロ以降が約4.5%速く再生されていた）。
- **推定したリズム**（写真になかった部分）：「ソ ソ ド ド／ファソシドレファソ」、大サビ最後の「…レレファファ」、後奏の「ファソ」「ド ラ シ」。

### アプリへの追加（`main.js`, `index.html`）
- 全646音を、楽譜と同じモチーフの組み合わせ（`SHIN_TAKARAJIMA_MOTIFS` / `SHIN_TAKARAJIMA_SECTIONS`）から生成。楽譜とアプリの646音が完全に一致することを確認済み。
- タイでつながる音は1打鍵。
- 指使い：「ソ レ ド レ／ファ レ ド レ レ」＝ 1 2 1 2／4 2 1 2 2、前奏フレーズ＝ 5 4 2 1 2 1 1 1 1 2 1 2 3（ユーザー指定）。それ以外（高いソ＝5、上昇フレーズなど）は推定。
- ラ（A4）・シ♭（B♭4）の周波数を追加。
- 起動時の曲選択と右上メニューの両方に「新宝島」を追加。
- 左手の自動伴奏はなし。

## 3. 反応の遅れと感度の改善

コミット `331fcdd`

| 変更 | 内容 | 効果 |
|---|---|---|
| 発音の先読みを0に | Tone.js は時刻を指定しない発音を既定で0.1秒後に予約していた。`lookAhead = 0` にして、判定と同じ瞬間に鳴らす | 約100ms短縮 |
| 速さの平滑化 1Hz → 4Hz | 1Hzだと打鍵の速さが実際の半分以下しか数値に出ていなかった | 軽いタッチの取りこぼし減少、判定の遅れ 約61ms → 約34ms（録画データ） |
| 21関節すべてを毎フレーム計算 | 以前は対象の指だけ計算し、指が切り替わると速さが0に戻っていた | 交互に弾く速いフレーズで有利 |
| 速さを手の大きさで割る | 基準をピクセル/秒から「手の大きさ/秒」に変更（親指5、ほかの指6） | 解像度・手とカメラの距離に左右されない |
| 検出する手を1本に | 2本だと片手しか映っていないとき、手のひら検出が毎フレーム走っていた | 認識が軽くなる |

録画データの再生シミュレーションで、速さの設定を決めた（下の表は、この時点での比較）。

| | 検出 | 誤反応 | 判定の遅れ（中央値） |
|---|---|---|---|
| 変更前 | 147 / 314 | 83 | 約61ms |
| 変更後 | 167 / 314 | 84 | 約34ms |

## 4. 取りこぼし対策（押しっぱなし判定の解消など）

コミット `83ae614`

### 見つかった原因
録画データを判定処理に通すと、**全時間の約7割が「押しっぱなし（押下中）」のまま**だった。打鍵後、指の下がり具合が固定の基準（リフト閾値）まで戻らないと次の打鍵を受け付けないため、手の構えやカメラ角度によっては、ずっと次を受け付けない状態になっていた。

### 変更内容
1. **相対的な復帰判定を追加**：打鍵後、一番下がった位置から一定量（親指0.12、ほかの指0.3）戻るか、指が上向きに動けば次の打鍵を受け付ける。
2. **閾値学習の式ずれを修正**：起動時に `public/dataset` のCSVから閾値を学習する際、CSVの `ry` 列（旧バージョンの式で、演奏中の値と最大約1.3倍ずれていた）ではなく、座標から演奏中と同じ式で計算し直す。
3. **親指の閾値**：座標から学習した場合は、旧来の下限クランプ（親指0.30）を外す（親指 0.30 → 0.13）。
4. **二重判定防止**：打鍵の最短間隔を80msに。

### 効果（録画データの再生シミュレーション）

| 指 | 変更前 | 変更後 |
|---|---|---|
| 親指 | 62% | 83% |
| 中指 | 48% | 86% |
| 薬指 | 38% | 79% |
| 小指 | 67% | 100% |
| **合計** | **52%** | **86%** |

誤反応は 81 → 93、1回の打鍵で余分に鳴った回数は 5 → 18。取りこぼしを減らすことを優先した設定。

> 人差し指は、データセットに座標が入っていない形式のため、閾値学習の式ずれは直せていない。

## 5. 演奏の記録と振り返り

コミット `dd5a4c6`（`recorder.js` 新規）

- 右上の **●** ボタンで記録を準備すると、曲を最初からカウントダウンし、演奏をコマ単位で記録する。
  - 縮小したカメラ画像（横200px のJPEG）
  - 21関節の平滑化座標
  - 5本の指それぞれの下がり具合（ry）と速さ（vy）
  - その時に弾くべき音・対象の指・判定状態・HIT
- 新宝島は前奏（第1〜20音）を弾き終えたら自動で停止。ほかの曲は最後まで（上限2分）。
- 終了後の振り返り画面：
  - タイムライン（♪鳴った／✕叩こうとした動きがあったのに鳴らなかった／?別の指の動き）
  - 印をタップすると、その瞬間の前後約14コマを実際のカメラ画像で表示（指の線と判定ラインを重ね、各コマの合格・不合格と判定状態を表示）
  - 鳴らなかった理由（押下中のまま／下がり不足／速さ不足／同じコマでそろわない）を数値付きで表示
  - 音ごとの結果表（鳴った時刻、前の音からの間隔、見逃し候補）
  - 記録をJSONで保存（画像を含む）
- 記録中はコマごとに画像を保存するため、判定処理が少し重くなる。

## 6. リズムが見えるノーツ・手の位置合わせ・演奏画面の拡大

コミット `01f69cd`（`positioning.js` 新規）

### ドレミが弾く前に落ちて消えるバグの修正
- 原因：次に弾く音のノーツが、画面右下の小さな手のイラスト（200px、画面下端から一部はみ出して配置）の指先に向かって落ち、手の上に重なって見えなくなっていた。弾くまで留まる位置が決まっていなかった。
- 対策：ノーツ表示を作り直し、**次に弾く音は判定ライン上で待ち、弾くまで消えない**ようにした。

### リズムが分かるノーツ表示
- 親指〜小指の5本のレーンにノーツを並べる。
- **ノーツの縦の間隔＝曲の中の時間**、**ノーツの長さ＝音の長さ**。全音符は長く、8分音符は短く表示される。
- 小節線（番号付き）と拍の線を背景に表示。
- 打鍵すると、次の音までの長さぶんだけなめらかにスクロールする。
- 判定ラインの下に「弾いた音」を残す帯があり、弾いた音は薄くなりながらゆっくり流れて消える（コミット `120fc2c`。それまでは弾いた直後に消えていた）。
- 指ごとに色分け。次に弾く音は白枠で光る。
- 当初は各レーンから手のイラストの指先へ細い線を引いていたが、邪魔になるため削除した（コミット `75e6de4`。曲の演奏・フリー演奏とも）。

### ノーツのデザイン（コミット `e002737`）
`docs/notes_design.html`（比較プレビューと配色の検証）で検討して決めた。

- **配色**：色覚の違いがあっても隣のレーンを見分けやすい配色に変更（親指=橙 `#E69F00`、人差し指=水色 `#56B4E9`、中指=黄 `#F0E442`、薬指=赤紫 `#CC79A7`、小指=青緑 `#00B386`）。以前の配色は、2型色覚で薬指（青）と小指（紫）がほぼ同じ色に見えていた。
- **数字なし**：ノーツ内の指番号と、判定ラインの指番号（1〜5）・それを入れていた角丸の枠を削除。判定ラインは白い線1本。
- **音名のみ**：文字色は背景の明るさに合わせて黒／白を自動で選ぶ。
- **低い音の点**：低いオクターブの音（新宝島の F4・G4・A4・B♭4）は音名の下に点を付け、高いソ（G5）と低いソ（G4）などを区別。
- **手のイラストの光る指**を、水色からノーツと同じ色に。
- 形は従来の長方形のまま。
- フリー演奏の判定ラインの「ド レ ミ ファ ソ」の枠は、指と音の対応を示すため残している。
- 全曲にリズム情報を追加（8分音符=1）。
  - よろこびのうた：16小節（4・8・16小節目は付点4分＋8分＋2分、10・11小節目に8分音符）
  - メリーさんの羊：8小節
  - 新宝島：164小節。各セクションの小節数が楽譜と一致することを確認（前奏12・Aメロ28・サビ24・間奏16・サビ2 32・大サビ24・後奏28）

### 起動時の手の位置合わせ
- カメラ起動後、演奏の前に「右手を置く位置」を点線の枠と手のシルエット、机の線で表示する。
- 毎フレーム、検出した右手を判定し、次のように案内する。
  - 手が見えているか
  - 枠の位置にあるか（「もう少し右へ」など方向を表示）
  - 大きさ（手の横幅が画面の38〜80%）
  - 指先が画面の端で切れていないか
- 良い位置で約1秒止まると「OK！この位置で判定します」と表示し、カウントダウンへ進む。「この位置で始める」ボタンで飛ばすこともできる。
- 右上の ⌖ ボタンで、いつでも位置合わせをやり直せる（のちに設定（⚙）パネルに移動）。
- 画面の文字は、のちに**一言だけ**にした（コミット `e6d4f31`）。「もう少し右へ」「右手を枠に入れてください」などを表示し、決まったら「OK！この位置のまま弾いてください」。説明文・チェック項目・注意書きは削除。
- 想定する置き方：スマホを手の正面・机の高さに立て、手を正面から写す（録画データの手の写り方に合わせた）。

### 演奏中の画面
- 手のガイドとノーツを大きく表示し、カメラは左下の小窓に縮小（コミット `53bc9ec` で約1.4倍に拡大）。
- 狭い画面では、進捗バッジを左上に寄せて右上のボタンと重ならないようにした。
- 進捗バッジに曲名を小さく表示（新宝島はセクション名も。例：「新宝島・前奏 1 / 646」）。

### 手のずれ対策（コミット `53bc9ec`）
- 位置合わせが終わった時点の手の位置を「最初の位置」として覚える。
- 演奏中は、カメラの小窓に**最初の位置（点線＋手のイラスト）**と**今の手の位置（緑の枠）**を重ねて表示する。
- 最初の位置から、横に画面幅の15%・縦に16%以上ずれるか、手の大きさが±40%以上変わる（近づく・離れる）状態が**2.5秒**続くと、次のように知らせる（コミット `3eeeed5` で緩和。当初は8%・9%・±22%・0.6秒で、頻繁に出て演奏の邪魔になっていた）。
  - **画面中央に大きな矢印**（← → ↑ ↓、近づける／離すは四隅の矢印）と、「左へ」などの短い言葉
  - 小窓の枠を赤くし、文章でも説明
- 次の場合は知らせない：直近2秒以内に音が鳴っている（弾けている）とき、手を見失って3秒未満のとき、矢印をタップしてその曲の警告を消したとき。「指先が画面の端で切れている」は演奏中は知らせない。
- 位置合わせ画面でも、動かす方向を同じ大きな矢印で表示する。最初の位置合わせの基準も緩めた（左右の許容 0.12→0.16、手の大きさ 画面幅の30〜88%）。
- 位置合わせ画面に「演奏中は、ここで合わせた位置から手を動かさずに弾いてください」と明記。
- 机に手を置いたまま（浮かせずに）でも合うよう、縦方向の許容範囲を広げた（±0.14 → ±0.20）。
- 位置合わせの手のイラストを濃く、輪郭付きにした（良い位置では緑になる）。

## 6.5 フリー演奏モード

コミット `a22a00b`

- 曲選択（起動時・右上メニュー）に「フリー演奏（ドレミファソ）」を追加。
- 楽譜はなく、**親指＝ド、人差し指＝レ、中指＝ミ、薬指＝ファ、小指＝ソ**を自由に弾ける。
- 5本の指それぞれに、曲の演奏と同じ判定（下がり具合・速さ・相対的な復帰）を持たせた。
- 指は隣どうしが連動して動くため、同じコマで条件を満たした指のうち**いちばん強く叩いた指だけ**を鳴らし、ほかの候補は指を上げるまで鳴らさない。模擬データで、中指を叩いたときに人差し指・薬指がつられて動いても「ミ」だけが鳴ることを確認。
- 画面：5本のレーンの下に音名（ド〜ソ）を表示し、叩くとそのレーンを音名の光が昇る（1.6秒）。最後に叩いた指のレーンと音名は、次に叩くまで光ったまま。進捗バッジに打鍵回数を表示。
- 位置合わせ・手のずれの矢印は、曲の演奏と同じように動く。演奏の記録（●）はフリー演奏では動かない。

## 6.6 演奏画面の描画負荷の削減

コミット `7a75b05`

手の認識（MediaPipe）は、画面の描画と同じメインスレッドで動く。6章で追加した演奏画面が毎フレーム全画面を高解像度で描き直していたため、認識に回る処理時間を奪っていた。

| 状態（CPU 1/4・画面3倍・ソフトウェア描画で計測） | 修正前 | 修正後 |
|---|---|---|
| 打鍵待ちの静止時：メインスレッド使用率 | 99% | **4%** |
| 打鍵待ちの静止時：画面の更新 | 33fps | **60fps** |
| 打鍵エフェクトが続く最悪ケース：使用率 | 84% | **44%** |

- 画面に変化がないフレームはノーツを描き直さない。
- ノーツの描画解像度を最大1.5倍に制限（iPhone の3倍では塗る画素数が4倍になる）。
- 次に弾く音の光り方を、重い shadowBlur から半透明の枠に変更。
- 動かないレーン背景を canvas から CSS の要素に移動。
- 演奏中の手のずれ確認を6フレームに1回に。
- 計測環境はGPUを使わないソフトウェア描画のため、実機（GPU描画）より重めに出る。手の認識そのものの時間は、この環境では測れていない。
- **この変更で入った不具合と修正（コミット `d5c0250`）**：幅が奇数の画面（例：393px×1.5＝589.5）で canvas の大きさが小数になり、毎フレーム作り直されて中身が消えていた。「変化がなければ描き直さない」と重なり、ノーツ全体が消えたままになっていた。canvas の大きさを整数に丸め、大きさが変わったとき・0.5秒ごと・アプリに戻ったときは必ず描き直すようにし、描画中のエラーで描画が止まらないようにした。iPhone/iPad 相当の8サイズで確認済み。

## 6.7 右上のボタンを設定（⚙）にまとめる

## 8. 調査で分かったこと

### 遅れの内訳（スマホでの目安。実機では未測定）

| 段階 | 目安 |
|---|---|
| カメラ（撮影〜ブラウザへの受け渡し） | 30〜80ms |
| 次のフレーム待ち | 平均8〜17ms |
| 手の認識（MediaPipe） | 15〜40ms |
| 平滑化（1 Euro Filter） | 約30ms |
| 発音（スピーカーまで。先読みは0に修正済み） | 10〜40ms（Bluetooth は150〜300ms） |
| **合計** | **約90〜200ms** |

### カメラのコマ数とリズムの限界
- 録画データの多くは約29fps（親指の録画だけ約59fps）だった。
- 1回の打鍵の下降は約0.1〜0.13秒。30fpsでは、その間に2〜4コマしか写らない。
- 30fpsでは判定のタイミングが毎回0〜33msの範囲でずれる。人はおよそ10〜20msのずれからリズムの乱れを感じるため、カメラだけでリズムどおりに弾くには構造的な限界がある。
- 電子ピアノは入力の読み取りが約1ms以下、押してから音が出るまで約3〜10ms。Piarno は読み取りが約33ms（30fps）、遅れが約90〜200ms。

### 親指が反応しにくい理由
- 親指の先の縦の動きは、中指の約3分の1（手の大きさ比で 0.39 対 1.06）。
- 基準にしている付け根の関節も一緒に動くので、差がさらに小さく見える。
- 修正前の閾値は下限0.30でクランプされていて、親指の打鍵がよく届いていなかった。

### データ側の問題
- 打鍵の印が、直前の印から30〜100msの近さで付いているものがあり、1回の打鍵に印が2つ付いたとみられる（同じ指をこの間隔で2回叩くのは無理）。
- 録画データの一部で、手が画面の端で切れていた。

## 9. まだ確認できていないこと・残っている課題

- **実機での確認**：この作業環境にはカメラがなく、手の認識モデルも読み込めないため、検出率・遅れ・新しい画面（ノーツ、位置合わせ、記録）は**模擬データとレイアウト確認でのみ**検証している。スマホ・iPad での確認が必要。
- **位置合わせの基準値**（枠の位置・大きさの範囲）は、録画データの手の写り方から決めた初期値。実際の置き方に合わせて調整が必要になる可能性がある。
- **人差し指の閾値学習**は、データセットの形式のため式ずれが残っている。
- **誤反応**は、取りこぼし対策で少し増えている。
- **今後の改善案**
  - マイクで机を叩いた音を聞く方式（タイミングを1ms以下の細かさで取れる。カメラは「どの指か」だけに使う）
  - 演奏前の指ごとキャリブレーション（その人・そのカメラ角度で閾値を決める）
  - 楽譜の拍に合わせて音を鳴らす方式
  - 録画データの印の重複の整理
